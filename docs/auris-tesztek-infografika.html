How we test Auris

Auris turns a book file into spoken audio. We check that the code works, that the pages open, and that the voice reads the right words. This page shows how.

No difficult words. Short sentences. One idea at a time.

1The short answer

Here is the result of the last full test run. It was run on this computer, on an ARM64 Windows machine.

655unit tests, all in Python
0real failures
2errors from missing software
1test was skipped
66test files in Python
17browser test files

The 2 errors are not bugs in Auris.

Two small helper programs do not exist for ARM64 Windows. They cannot be installed here. Two tests try to use them, so those two tests stop early.

The same 2 errors happen on a clean copy of the project. They are expected. They are written down so nobody wastes time on them again.

2Four kinds of checks

Each kind answers a different question. Each one catches different mistakes.

Layer 1

Unit tests

These test small parts of the program. One part at a time. No web browser is used.

Good for: finding a mistake early. They run fast. There are 655 of them. They finish in about 30 seconds.

Layer 2

Browser tests

These open the real Auris pages in a real web browser. They click buttons. They fill in boxes.

Good for: checking what a person actually sees. A button must react. A list must load. There are 17 of these files.

Layer 3

Sound checks

Auris makes speech. So we listen to it with a computer. A speech recognition program writes the words down. Then we compare that text with the original book text.

Good for: catching a wrong pronunciation or a skipped sentence. This is the only way to test the voice on its own.

Layer 4

Speed and memory checks

These do not check for mistakes. They measure how fast the work is done. And how much memory it needs.

Good for: making a long book finish in a reasonable time. Also good for keeping memory use low.

3What the numbers mean

Two numbers appear many times. Here is what they mean, in plain words.

RTF — how fast is it?

RTF means how much audio we get per second of work. A small number is good. For example, 0.144 means we make 7 seconds of audio in 1 second of work. That is 7 times faster than real time.

WER — how many words were wrong?

WER means word error rate. A computer listens to the audio. It writes down what it hears. We compare that with the text we wanted. WER is the share of words that did not match. So 11 percent means 11 words out of 100 were different. A small number is good.

CER — how many letters were wrong?

CER means character error rate. It counts letters instead of whole words. It is useful for names and numbers, where one wrong letter can ruin a word. A small number is good.

4What we listen for in the audio

After every chapter, five things are checked. If one of them is wrong, the chapter is marked.

  • Clipping. The loud parts were cut off. The audio was too strong.
  • Long pause. A silence longer than 1.5 seconds was found inside the sentence.
  • Silent. No speech was found at all. The chapter may be empty.
  • Too fast. The voice spoke faster than 0.035 seconds per letter.
  • Too slow. The voice spoke slower than 0.25 seconds per letter.

One known false alarm.

The long pause check fires too often. The threshold is fixed at 1.5 seconds. But a normal break between two sentences is often 1.5 to 2.1 seconds long.

So the check says there is a problem, when there is none. We found the cause. We wrote it down.

5How to run the tests

You run these in a terminal window. The first one is the most useful. It checks the small parts.

Run the unit tests

go to the reader folder first
cd "C:\Users\istva\Dev\portfolio\Projects\audiobook narrator\auris\reader"
now run the tests
.venv\Scripts\python.exe -m unittest discover -s tests -t tests -p "test_*.py"

The last line tells you what happened. Look for the word OK.

Run the sound check on the whole book

.venv\Scripts\python.exe -m core.hu_wer

This reads 24 Hungarian sentences out loud. Then it listens to them. Then it prints the WER.

Run the browser tests

start the small fake server in one window
set AURIS_QA_DATA=/tmp/aurisqa
set AURIS_QA_PORT=17881
.venv\Scripts\python.exe tests\ui_fixture_server.py
then run the browser test in another window
set AURIS_QA_URL=http://127.0.0.1:17881
node tests\browser_experience.cjs

6The daily loop

When something changes in Auris, these four steps are always the same.

Step 1

Change the code

Make the change you need.

Step 2

Run the tests

All of them, not just one.

Step 3

Read the numbers

Look at the results. Not just the last line.

Step 4

Keep it, or undo it

Keep the change only if the numbers are still good.

Why all of them?

A change can make the code faster and break a page at the same time. A change can fix a sound problem and break a button. One test cannot see everything.

7What these tests cannot do

This part is important. A test that looks strong can still be weak in some way.

Two tests cannot run on this computer

They need two helper programs. These do not exist for ARM64 Windows. The tests stop early with an error.

This is not a bug in Auris. It is a missing building block.

The sound check uses only 24 sentences

That is a small sample. A result like 0.19 percent WER looks perfect. But it is only two or three sentences.

Treat it as a sign of quality. Do not treat it as a final answer.

There is no test for the NPU

We tried three ways to run the model on the special AI chip. All three failed. The chip never ran the model.

So we cannot say if the chip would be faster. There is no number. A missing number is not the same as a slow number.
